# 微信保险销售循环分析

从 Obsidian LLM-CRM vault（`/Users/Charles/Library/Mobile Documents/iCloud~md~obsidian/Documents/LLM-CRM`）的 `raw/chatlog/` 读取微信聊天记录，AI 分析每个好友所处的保险销售循环阶段。

## 五个阶段定义

| 阶段 | 定义 | 关键特征 |
|------|------|----------|
| 拓 | 加好友后闲聊 | 无保险内容 |
| 圈 | 互相参加活动 | 无保险内容，建立信任 |
| 触 | 聊保险理念 | 保障、风险、医疗等概念 |
| 访 | 线下见面聊需求 | 需求分析、计划书 |
| 转 | 已签单/已投保 | 投保流程完成，保单生效 |

## 执行流程

### 1. 确定分析范围

默认使用**增量模式**：只分析 `raw/chatlog/` 中有聊天记录文件、且满足以下任一条件的好友：
- `wiki/entities/<wxid>.md` 不存在（新好友，需用户手动指定才分析）
- 聊天记录文件的修改时间晚于对应 entity 笔记中"上次分析时间"

用户可指定以下方式覆盖默认行为：
- 指定一个或多个 wxid 进行分析
- 全量分析所有有聊天记录的好友

**排除规则**：同时带有 `©AIA` 和 `Career_Ins_Sales` 标签的联系人属于友邦保险代理人（同业），不纳入保险销售循环分析。在确定分析范围时直接排除，不计入分析对象。

增量模式下，跳过无新消息的好友时需告知用户跳过了多少个，同时单独列出被排除的同业联系人。

### 2. 准备工作

确认以下信息（若用户未提供，则询问）：
- Obsidian vault 路径：`/Users/Charles/Library/Mobile Documents/iCloud~md~obsidian/Documents/LLM-CRM`
- WeFlow API Token（如需要从 API 获取联系人信息补充手机号等字段）

### 3. 读取聊天记录

对每个待分析的好友：
- 读取 `raw/chatlog/<wxid>.md` 获取完整聊天记录
- 读取 `wiki/entities/<wxid>.md`（如存在）获取现有阶段和历史

若聊天记录文件不存在，跳过该好友并记录。

### 4. AI 阶段判定

**纯 AI 分析，严格基于聊天内容，不参考现有标签。**

分析聊天记录时关注以下信号：

**拓阶段信号：**
- 刚加好友不久的寒暄
- 自我介绍、交换名片信息
- 没有任何保险相关话题

**圈阶段信号：**
- 互相邀请参加活动（讲座、沙龙、聚餐等）
- 日常闲聊建立关系
- 点赞、评论朋友圈互动
- 仍无保险相关内容

**触阶段信号：**
- 开始聊到健康、医疗、养老等话题
- 对方提到保障缺口、风险担忧
- 聊到具体险种概念（重疾、医疗、寿险、意外等）
- 讨论保险理念或理赔案例
- 对方主动询问保险相关问题

**访阶段信号：**
- 约定或确认线下见面的时间地点
- 见面后的跟进消息（"上次聊得很愉快"等）
- 发送了需求分析或计划书的引用
- 讨论具体保费、保额、保障方案
- 提到"和家人商量""对比一下"等决策前信号

**转阶段信号：**
- 明确产生了交易（已签单/已投保），仅有购买意向不算
- 保单号、生效日期等已投保信息
- 投保流程走完，扣款成功
- 转介绍请求（已成交客户才会被要求转介绍）

注意：讨论方案、催出计划书、表达购买意向都属于触/访阶段，不能判为转。

判定时遵循以下原则：
- 取聊天记录中达到的最高阶段
- 转必须有明确交易证据（签单/投保完成），仅有意向不能判为转
- 若长期（>30天）无保险相关内容，可以考虑阶段回退（如从"触"退回"圈"）
- 阶段判定基于对话内容的实质，而非表面关键词匹配

### 5. 生成判定依据

从聊天记录中提取 3-5 条最能支撑当前阶段判断的具体对话片段，格式为：
```
- YYYY-MM-DD: 对方说"..."（简要概括关键内容）
```

### 6. 记录分析历史

**每次分析都必须追加一条阶段变更历史记录**，包括首次分析。每条记录必须包含当时的判定依据。

确定旧阶段：
- 若 `wiki/entities/<wxid>.md` 已存在：提取其 frontmatter 中的"当前保险销售循环阶段"作为旧阶段
- 若不存在（首次分析）：旧阶段记为"无"

将本次 AI 判定结果作为新阶段，连同 step 5 生成的判定依据，追加到阶段变更历史。格式：
```
- YYYY-MM-DD: <旧阶段> → <新阶段>
  - YYYY-MM-DD: <具体对话信号>
  - YYYY-MM-DD: <具体对话信号>
  - ...（3-5条）
```

即使阶段未变化（旧阶段 = 新阶段，如"拓 → 拓"），也必须记录，以保留本次分析的判定依据和时间节点。

### 7. 生成建议动作

根据当前阶段，自动生成下一步建议动作：

- **拓阶段**：了解对方兴趣爱好，寻找建立关系的机会；邀请参加公司/个人举办的线上线下活动
- **圈阶段**：持续互动建立信任；关注对方朋友圈动态并适时互动；通过活动加深关系
- **触阶段**：了解对方家庭结构和责任；适时深入保障需求话题；分享有价值的保险科普内容
- **访阶段**：准备好需求分析方案和计划书；确认线下见面的核心议题；提前预判可能的异议
- **转阶段**：跟进投保流程进展；确保健康告知和核保顺利；确认保单生效后的回访安排

### 8. 写入/更新 Obsidian 笔记

使用 obsidian-cli 技能写入 `wiki/entities/<wxid>.md`。

**Frontmatter 字段（必须包含）：**
```yaml
---
当前保险销售循环阶段: <拓/圈/触/访/转>
上次分析时间: <当前时间 ISO 格式>
最后消息时间: <聊天记录中最后一条消息的时间>
tags:
  - wechat
---
```
身份信息（微信ID、显示名、备注等）不在此重复，通过 wikilink 引用原始聊天记录文件获取。

**正文格式：**
```markdown
# 保险销售循环

聊天记录：[[raw/chatlog/<wxid>]]

当前阶段：<阶段>

## 判定依据
- YYYY-MM-DD: <具体对话信号>

## 阶段变更历史
- YYYY-MM-DD: <旧阶段> → <新阶段>
  - YYYY-MM-DD: <具体对话信号>
  - YYYY-MM-DD: <具体对话信号>

## 建议动作
- <建议1>
- <建议2>
```

注意事项：
- 若 entity 笔记已存在且有其他一级标题（非"保险销售循环"），保留这些标题不变，只更新"保险销售循环"部分
- 若 entity 笔记不存在，创建新笔记，完整写入所有内容
- 若聊天记录中缺少手机号等信息，对应 frontmatter 字段留空字符串
- 最后消息时间从聊天记录中提取最后一条的 createTime 转换

### 9. 输出分析汇总

分析完成后，向用户输出汇总：

```
本次分析汇总：
- 扫描好友：N 个
- 跳过（无新消息）：M 个
- 分析：K 个
- 阶段变化：J 个
   - wxid_xxx: 圈 → 触（开始聊重疾险）
   - wxid_yyy: 触 → 圈（30天无保险话题）
- 阶段维持：L 个
```

## 首次分析模式

用户指定 wxid 触发首次分析时：
- 不要求 `wiki/entities/<wxid>.md` 已存在
- 创建新笔记时，阶段变更历史记录一条：`无 → <判定阶段>`，并附带判定依据
- 其余流程与增量分析相同

## 无新消息时跳过

聊天记录文件的修改时间不晚于 entity 笔记中"上次分析时间"的好友直接跳过，**不做任何文件写入**（不更新"上次分析时间"，不追加历史记录）。只有实际读取并分析了新消息的好友才写入笔记。
